## Principles

- Classic layering: `presentation → application → domain → infrastructure`.
- Each layer depends only on the layers strictly below it.
- Cross-cutting concerns (logging, security) live in dedicated modules consumed by all layers.

## Suggested package boundaries

| Layer            | Owns                                                          |
| ---------------- | ------------------------------------------------------------- |
| `presentation`   | Controllers, view models, CLI surfaces, response mapping.     |
| `application`    | Application services, transaction orchestration, DTOs.        |
| `domain`         | Entities, business rules, domain events.                      |
| `infrastructure` | Repositories, gateways, message brokers, framework wiring.    |

## Diagrams to fill in during `sdd spec`

- Layered diagram with explicit allowed dependencies.
- Sequence diagrams for at least one happy path and one failure path.

## Common pitfalls

- Anemic domain (only DTOs) — push behavior down into the domain layer.
- Skipping a layer (controller → repository) — keep the boundaries enforced via static analysis.
- Bidirectional references between layers.
